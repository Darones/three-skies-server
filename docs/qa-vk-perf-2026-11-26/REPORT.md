# Почему «в редакторе не лагает, а в VK лагает» — замеры и план

Дата: 26.11.2026. Ветка: `mobile-ui` (рабочее дерево, без коммитов).
Прод: `https://three-skies-server.relaxdev.ru` (deploy `148909d`, PCK 27 839 484).
Замеры: Chrome 158.0.8127.88, Windows, ANGLE-D3D11 (Radeon RX 570), мобильная эмуляция.

---

## 0. Короткий ответ

1. **VK как оболочка почти ничего не добавляет.** `/game-vk/` — это 1017-байтный shell с одним
   `location.replace('/game/...')`, `vk-bridge.min.js` — 4.7 КБ и один `VKWebAppInit`.
   Виноват не VK, а **веб-сборка Godot**: в VK играют в тот же `/game/`, что и в Chrome.
2. **Главная причина лагов — синхронная линковка шейдеров в WebGL (Compatibility).**
   За один сеанс обучения: **191–256 программ**, суммарно **66–86 секунд** блокировки главного
   потока, худшая одиночная линковка **2.3–2.9 с**. В профайлере 76% времени — `gl.getProgramParameter`.
   Меню на старте: **38 программ / 15 с** — это большая часть из 25 с загрузки.
3. **Это баг пути ANGLE-D3D11, а не «слабый телефон»:** тот же билд на `--use-angle=gl`
   линкует те же 202 программы за **4.5 с (макс 90 мс)** вместо 77 с (макс 2.5 с), загрузка 14.5 с вместо 25 с.
   На Windows (в т.ч. в VK на ПК) Chrome по умолчанию идёт через D3D11 → 2.3 с на шейдер.
4. **DPR/canvas — не причина залипаний.** При DPR 3 canvas 2532×1170, но на десктопном GPU
   переход DPR 3 → 1 не меняет ни одного залипания и даёт то же плато 60 fps. Это рычаг для
   заливки/нагрева на телефоне, но не лекарство от фризов.
5. **Сеть:** 10.2 МБ (wasm, gzip) + 27.8 МБ (PCK, **без сжатия**, gzip даёт 96% — бесполезно) ≈ 38 МБ.
   На VK-мобильном это десятки секунд до первого кадра.

## 1. Чем VK отличается от редактора (по факту, а не по слухам)

| | Редактор (нативно) | Chrome/Web | VK/OK webview |
|---|---|---|---|
| Код | x86_64 native | WebAssembly | WebAssembly |
| Графика | Forward+ / Vulkan-D3D12 | **только Compatibility / WebGL2** | то же |
| Потоки | многопоточно | **single-threaded** (`GODOT_THREADS_ENABLED=false`, `SharedArrayBuffer` нет, COOP/COEP не отдаются) | то же |
| Шейдеры | компилируются при импорте, кэш на диске | **линкуются в рантайме, на главном потоке**, кэш только в памяти сессии | то же |
| Canvas | окно ОС | `canvasResizePolicy=2` → backing store = CSS × DPR | то же, DPR обычно 2.5–4 |
| Оболочка | — | — | +1 HTML 1 КБ, +редирект, +VK Bridge 4.7 КБ, iframe/webview |

Отдельно про iframe: документация Godot прямо предупреждает, что в iframe для `user://`
нужны **third-party cookies** (IndexedDB), иначе настройки/локальные данные не сохраняются.
Прогресс в игре серверный, но `settings.cfg` (в т.ч. выбранное качество) может сбрасываться
при каждом запуске внутри VK — это стоит проверить на устройстве.

Подтверждено логами самого движка:

```
OpenGL API OpenGL ES 3.0 (WebGL 2.0 ...) - Compatibility - Using Device: WebKit - WebKit WebGL
Build configuration: Emscripten 4.0.20, single-threaded, no GDExtension support.
WARNING: Screen-space AA is only available when using the Forward+ or Mobile renderer.
```

Последняя строка — ещё и след Forward+-настроек в `project.godot` (`screen_space_aa=1`),
которые в вебе просто игнорируются.

Официальная документация Godot 4.7 (exporting_for_web) подтверждает: web = WebGL2 + Compatibility,
Forward+/Mobile не поддерживаются; single-thread экспорт «не так производителен»; на мобиле
«CPU и GPU в дефиците, и это тем более верно для WebAssembly вместо нативного кода».

## 2. Замеры

Методика: `tools/vk_perf_cdp.mjs` (новый файл) — Chrome по CDP, мобильная эмуляция
(844×390 @ DPR 3 и 390×844 @ DPR 3, touch, Android UA), сбор `rAF`-дельт, long tasks,
resource timing, `Performance.getMetrics`, CPU-профиль, а также **обёртка WebGL**:
время `compileShader` и время `getProgramParameter(LINK_STATUS)`, которое и есть залипание.

### 2.1 Бут и меню (`/game/`, 844×390, DPR 3)

| Метрика | Значение |
|---|---|
| canvas backing store | **2532×1170** (CSS 844×390, DPR 3) = 2.96 Мп |
| внутренний рендер | content scale 960×540 (aspect expand ≈ 1168×540), 3D `scaling_3d_scale=0.5` ≈ 584×270 |
| загрузка до первого кадра | **23.4–31.7 с** (медиана ≈25 с) |
| самый длинный long task | **18.5 с** (старт 6.7 с — после скачивания) |
| шейдерных программ к меню | **38**, блокировка **15.1 с**, худшая 2.43 с |
| wasm | 39 514 754 Б → **10 164 141 Б** по сети (gzip), 2.5–6.4 с |
| PCK | 27 839 484 Б **без Content-Encoding**, 3 range-запроса, 2.7–6.5 с |
| JS heap | 9.6 МБ (DOM 65 узлов — не проблема) |

### 2.2 Обучение (локальный бой, без авторизации)

| Прогон | программ | блокировка линков | худшая | fps после прогрева |
|---|---|---|---|---|
| DPR 1, headless | 191 | **77.3 с** | 2.57 с | 60–61 |
| DPR 1, **headed** | 256 | **84.1 с** | 2.69 с | 60–61 |
| DPR 3, headless | 256 | 85.4 с | 2.65 с | 60–61 |
| DPR 1, **ANGLE-GL** | 202 | **4.5 с** | **0.090 с** | — |

`Performance.getMetrics` за сеанс обучения: **TaskDuration 106 с, ScriptDuration 87 с** —
87 секунд исполнения скрипта на главном потоке, из них ~85 с — линковка шейдеров.

Профиль CPU (24 с сэмплирования):

```
getProgramParameter   72.8 с   76.3%
(idle)                 5.8 с    6.1%
getParameter           5.7 с    5.9%
getShaderParameter     3.1 с    3.2%
compileShader          0.14 с   0.1%   <- сама компиляция асинхронная, блокирует LINK
```

FPS по секундам в обучении (DPR 3): `26, 1, 4, 16, 11, 17, 47, 47, 14, 48, 3, 4, 11, 13, 29, 30, 61, 61, 60…`
То есть **залипания по 1–6 секунд, потом стабильные 60**. Это ровно то, что игрок называет «лагает».

Скриншот загрузки обучения в этот момент: `59% · Оружие и предметы · 54.8 с` — при штатном
бюджете WarmupFlow 21–23 с и жёстком стопе 28 с. На D3D11 прогрев не успевает.

### 2.3 Чем именно дороги эти программы

Все худшие линковки — стандартный spatial-шейдер (`BASE_PASS`, `APPLY_TONEMAPPING`,
`DIFFUSE_BURLEY`) с активным `USE_RADIANCE_MAP` (ambient от скайбокса):

| вариант | n | сумма | средняя |
|---|---|---|---|
| с `USE_RADIANCE_MAP` (D3D11) | 84 | 69.8 с | **831 мс** |
| без него (D3D11) | 29 | 6.4 с | 222 мс |
| с `USE_RADIANCE_MAP` (ANGLE-GL) | 61 | 3.3 с | **55 мс** |
| без него (ANGLE-GL) | 2 | 0.09 с | 46 мс |

На GL разницы почти нет → **проблема в трансляции GLSL→HLSL внутри ANGLE-D3D11**:
чем больше шейдер (радианс-карта, лайты, варианты), тем дольше блокировка. 2.3 с на программу —
это не «слабый телефон», это конкретный путь драйвера.

Дубли: из 113 «дорогих» линков **37 (33%) — повторная линковка варианта с тем же набором
активных define** (15 групп, до 3 раз). Похоже, программы освобождаются/пересоздаются
(кандидат — отдельный SubViewport миникарты или пересоздание материалов после прогрева).
Это до ~25 с лишнего времени; гипотезу надо проверить отдельным прогоном (выключить миникарту).

### 2.4 `/game-vk/` vs `/game/`

| | `/game/` | `/game-vk/` |
|---|---|---|
| первый документ | index.html 13.6 КБ | index.html **1017 Б** + JS-редирект |
| дальше | — | тот же `/game/` (canvas, DPR, шейдеры — идентичны) |
| лишние байты | — | **~1 КБ и один тик event loop** |
| шейдерные программы/блокировка | 38 / 15.1 с | 38 / 15.1 с |
| VK Bridge | загружен (4.7 КБ) + `VKWebAppInit` | то же |

Вывод: **VK-специфичного overhead в shell нет**. Всё, что болит, воспроизводится в обычном Chrome.

### 2.5 DPR и canvas

| прогон | canvas | fps (меню) | залипания |
|---|---|---|---|
| 844×390 DPR 3 | 2532×1170 | 52–61 | те же 2.3 с линков |
| 844×390 DPR 1 | 844×390 | 31–60* | те же 2.3 с линков |
| 390×844 DPR 3 | 1170×2532 | 31 | — |
| 390×844 DPR 1 | 390×844 | 31 | — |

\* 31/60 в меню скачет из-за троттлинга `rAF` в headless (30 Гц); в обучении оба варианта
выходят на плато 60–61 fps. **Ни один замер не показал, что DPR — причина фризов.**

Честная оценка: DPR 3 на телефоне — это ~3 Мп финального блита/композитинга на кадр
при 0.16 Мп 3D. Для мобильного GPU это заметная, но не определяющая статья (нагрев, батарея,
просадки в тяжёлых кадрах), поэтому clamp DPR — разумная гигиена, а не «лекарство».

## 4. Топ-5 VK-специфичных правок (по убыванию эффекта)

1. **Убрать радианс из ambient на low/mobile.** `WorldEnvironment`: `ambient_light_source = COLOR`
   (подобранный цвет), `reflected_light_source = DISABLED`. Ожидание: минус `USE_RADIANCE_MAP`
   из всех spatial-программ, средняя линковка с 0.8–1.6 с падает к 0.07–0.2 с на D3D11.
   Риск: сцена темнее/площе — подобрать цвет ambient + чуть поднять exposure.
2. **Гарантированный полный прогрев до первого интерактивного кадра, без тайм-пейсинга.**
   Греть по списку материалов, показывать «N/M программ», не освобождать прогретое.
   Ожидание: все 191–256 линков уезжают на экран загрузки (это те же секунды, но без «игра
   зависла в бою»), плюс минус дубли (33%).
3. **Сократить число вариантов в 2 раза.** `cull_disabled` → `cull_back` там, где не нужен
   (52 дорогих линка), rim off (4), alpha-scissor только где реально нужно (2), instancing только
   для реальных толп (51). Ожидание: 191 → ~90–110 программ, т.е. −40…50% времени.
4. **PCK и ассеты.** 27.8 МБ несжимаемы: резать текстуры (WebP/ETC2), выкинуть неиспользуемое
   из `all_resources`. Ожидание: −5…10 с на первом входе в VK-мобильном.
5. **VK-only гигиена кадра:** `devicePixelRatio` clamp до 1.0–1.5 и/или cap 30 fps на VK.
   Ожидание: −50…65% пикселей финального блита, меньше нагрева и троттлинга на длинной сессии;
   на десктопе FPS не изменится (не узкое место). Риск: мягче картинка HUD.

Отдельно, **не** делать сейчас:
- threads/SharedArrayBuffer: нужны `COOP/COEP`, в VK iframe это ломает сторонние вставки
  и не даёт выигрыша в линковке шейдеров (она и так на главном потоке);
- «починить DPR и всё пройдёт»: замеры этого не подтверждают;
- менять геймплей/ботов — к этим цифрам отношения не имеет.

### Что снять в реальном VK (чек-лист)

| Что | Зачем |
|---|---|
| `renderer` из панели (`ANGLE (... Vulkan ...)`, `Metal`, `Adreno`, `Mali`) | понять, какой backend у webview; D3D11-эффекта там не будет, но размер шейдера бьёт и по Vulkan/Metal |
| `dpr` и `canvas` | реальный DPR в VK (2.5–4?), сколько пикселей платит игрок |
| `shader links` / `block` / `worst` на входе в меню и в первом бою | главная метрика; сравнить с нашими 38/15 с и 191–256/66–86 с |

| память (в настройках игры + `heapMB`) | не убивает ли webview вкладку (iOS особенно) |
| сохраняется ли `settings.cfg` между запусками | в VK iframe `user://` требует third-party cookies; иначе качество сбрасывается на low каждый раз |

Достаточно одного скриншота развёрнутой панели из VK на iPhone и на Android — этого хватит,
чтобы подтверть/опровергнуть, что на телефоне доминирует тот же фактор.

## 7. Ограничения измерений (чтобы не обмануться)

- GPU — десктопная RX 570, не мобильная. Абсолютные мс линковки на телефоне будут другими;
  воспроизводится **механизм** (блокирующий LINK на главном потоке), а не конкретные 2.3 с.
- Мобильный CPU эмулировался только троттлингом (×6) и то на меню; на бою не троттлил.
- В VK/OK без реальных launch params авторизация не проходит — мерил загрузку, меню,
  обучение и шаблон боя; онлайн-матч с WarmupFlow не проверен.
- `fps` меню в headless иногда упирается в 30 Гц `rAF` — такие прогоны помечены и в выводах
  не использованы; обучение воспроизведено и в headed-режиме.
- VK/OK-документация по лимитам webview в этом окружении недоступна (403/404), поэтому
  про лимиты VK я ничего не утверждаю: их надо снять на устройстве через `?perf=1`.
