# Фризы и опоздание звука в начале боя (27.11.2026)

Задача: воспроизвести старт боя (Main/`start_match`), первые 5 секунд
(вход в бой, `live` + 5 с), найти причину фризов и опоздания звука начала
боя. Приоритет — **телефон через VK** (844×390, Compatibility, `mobile_ui`).

Ничего не закоммичено и не задеплоено. `scripts/game.gd`, `hero.gd`,
`remote_player.gd`, `hud.gd`, `lobby.gd`, `server/*` не менялись.

## Что сделано

Файлы:

- `scripts/warmup_flow.gd` — удерживает загруженные ресурсы, новый этап
  «Звук боя» (музыка, эмбиент, все SFX), этап «Эффекты боя» (сцены из
  `FIRST_CLASH_WARM_VFX`), `retained_resources`.
- `scripts/loading_screen.gd` — передаёт `retained_resources` узлу
  `BattleAssetKeeper` на `SceneTree.root`, который живёт 8 с после перехода
  и сам освобождает ссылки; аудио-запрос для путей без `WarmupFlow`.
- `scripts/audio_preloader.gd` (новый) — список аудио боя: тема, эмбиент и
  `SFX_PATHS` читаются **из констант `game.gd`**, чтобы список не разъезжался.
- `tools/battle_start_probe.gd` + `.tscn` (новый probe) — таймлайн кадров от
  `instantiate` Main до `live` + 5 с, аудио-события, стоимость загрузки аудио,
  `--action=spawn|hud` для замера одного кадра, `--drop-retained` (A/B).
- `tools/battle_start_e2e_probe.gd` + `.tscn` (новый probe) — реальный путь
  `LoadingScreen` → `Main` (+keeper, аудио, первые 5 с), `--no-keep-battle-assets`
  (A/B), `--keeper-check` (проверка освобождения памяти).

## Причина 1 (моя зона): прогретые ресурсы не удерживались, матч читал их заново

`WarmupFlow` грузит модели бойцов и реквизит арены, рисует их в скрытом
viewport и освобождает экземпляры. Кэш `ResourceLoader` **слабый**: как
только последняя ссылка ушла, ресурс выгружается. Кэш проверен до
`instantiate` Main: `Main.tscn=false, character.tscn=false, music=false,
ambient=false` — всё «прогретое» матч читал из PCK заново.

Замер одного кадра (`BattleStartProbe --action=spawn`, Compatibility,
один кадр = шесть `_spawn_hero`, как в `start_match`):

| | было | стало |
|---|---|---|
| Воин (первый) | 118.8 мс | 4.1 мс |
| Маг (первый) | 93.4 мс | 2.5 мс |
| Охотница (первая) | 86.2 мс | 2.2 мс |
| второй круг (те же классы, из кэша) | 6.6 / 6.6 / 6.2 мс | 2.2 / 2.4 / 2.3 мс |
| **итого один кадр** | **296.7 мс** | **15.8 мс** |

На мобильном профиле `start_match` раскидывает спавны по кадрам
(`await process_frame`), поэтому там это не один кадр, а ~300 мс
«залипаний» подряд перед `live`.

## Причина 2: аудио боя грузилось синхронно в кадре открытия сцены

`game.gd:1377` `load(MUSIC_PATH)`, `game.gd:1394` `load(AMBIENT_PATH)`,
`game.gd:1407+` `load(SFX_PATHS[key])` — всё внутри `_setup_audio()`, то есть
в `_ready`, в том самом кадре перехода. Холодная стоимость (замер
`CACHE_MODE_IGNORE`): музыка **4.5–5.2 мс**, эмбиент **2.0–2.3 мс**,
14 SFX **18.6–21.5 мс**, всего ~26 мс. После предзагрузки —
**0.01–0.02 мс** (кэш-хит), плюс первый `play()` больше не ждёт холодный
поток.

Звук на этой машине стартует **через 0–3 мс после `live`** (`play_sfx`
`game.gd:1983`), `AudioServer.get_output_latency()` = 10 мс, позиция музыки в
`live` 2.9 мс (её перезапускает `game.gd:1970`). То есть игра звук не
задерживает: 5 секунд на телефоне — это длительность самого фриза (главный
поток занят, и очередь звука/микширование веб-аудио стоит вместе с ним).

## Причина 3 (зона агента C, `game.gd`): новый «реальный» прогрев первой стычки

Добавлен в `738c614`: `game.gd:327` `_start_first_clash_warm()` →
`game.gd:446` `call_deferred("_warm_first_clash_world")` →
`game.gd:453-700`. Внутри `game.gd:485` шесть синхронных
`load(path) as PackedScene` + instantiate + Label3D-варианты, по 2 кадра на
эффект — **в кадрах прямо перед `live`**.

`first_clash_warm_ms` (тот же probe): **873 мс** (desktop) / **751 мс**
(mobile) до моих правок; после предзагрузки этих сцен в прогреве —
**621 мс** / **520 мс**. Остаток — это instantiate/draw, он по-прежнему в
одном-двух кадрах по 40–105 мс.

## Причина 4 (зона агента C): кадр открытия Main

Один кадр `instantiate` + `_ready` = **354–393 мс** на мобильном профиле
(`game.gd:267-330`): `ArenaKit.ensure_*` (300-305), `_prepare_effect_pools()`
(308), `hud = preload(...)` + `add_child(hud)` (309–312). Отдельный замер
сборки HUD: `hud.gd/_ready` = **70.7 мс** (второй экземпляр, скрипт уже
загружен). Это самый большой оставшийся кадр в первых 5 секундах.

## Что осталось агенту C (`scripts/game.gd`)

Номера строк на момент отчёта (файл правят параллельно — сверять по тексту):

1. **`game.gd:453-700` `_warm_first_clash_world`** — 6× `load()`
   (`game.gd:485`) + instantiate в одном-двух кадрах, вызывается из `_ready`
   (`game.gd:327`) через `call_deferred`. Это 520–750 мс перед `live`.
   Варианты: (a) делать этот прогрев на экране поиска (в `WarmupFlow`),
   (b) оставить, но разнести по кадрам с `create_timer` (1 эффект на ~0.15 с),
   (c) на мобиле не делать его при `battle_prewarmed` — `WarmupFlow` уже
   рисовал эти VFX. Закрытые сцены уже предзагружены мной
   (`FIRST_CLASH_WARM_VFX` в `retained_resources`), так что `load()` там
   теперь кэш-хит, остаётся только instantiate/draw.
2. **`game.gd:1944`** — `start_match` ждёт этот прогрев до 10 с, поэтому
   задержка «Матч найден → бой» = спавн + прогрев.
3. **`game.gd:267-330` `_ready`** — один кадр 354–393 мс: `300-305`
   (арена/декор), `308` (`_prepare_effect_pools`), `309-312` (сборка HUD,
   замер 70.7 мс). Достаточно `await get_tree().process_frame` между этими
   тремя блоками — как уже сделано для мобильных спавнов, ни один кадр не
   будет >100 мс.
4. `game.gd:1377/1394/1407` — синхронные `load()` аудио: **править не
   нужно**, после предзагрузки в прогреве это кэш-хиты (0.01 мс). Если
   когда-то будете менять — не переносите `play()` раньше `_ready`.
5. `game.gd:1970` `music.play()` + `game.gd:1983` `play_sfx("match_start")`
   — по замерам звук стартует через 0–3 мс после `live`, менять не нужно.

## Как проверить на реальном телефоне (VK)

Фриз на ~5 с зависит от GPU/драйвера телефона, на этой машине он не
воспроизводится (десктопная GL Compatibility: худший кадр 373 мс, после
`live` — 4.5 мс). На телефоне:

1. Открыть игру в VK с `&perf=1`
   (`?perf=1` тоже работает, VK-shell сохраняет query) — в левом верхнем углу
   появится панель `[VKPERF]`.
2. Зайти в бой и сразу снять панель/консоль: строки идут каждые 5 с,
   `window.__vkperfReport()` возвращает JSON. Смотреть:
   - `longTasks.maxMs` / `[VKPERF] LT ... (max X s)` — там 5-секундный фриз
     виден как один longtask ~5000 мс;
   - блок `SH` (shader links) — сколько драйвер линкует шейдеров и сколько
     это стоит; на VK/ANGLE это самый вероятный источник многомесячных
     пауз;
   - `boot.loaderHiddenMs` — момент реального «входа в бой».
3. Важно: `tools/vk_perf_diag.js:220` (`if (dt > 0 && dt < 2000)`) **выкидывает
   из статистики кадры длиннее 2 с**, поэтому `frameP95Ms` фриз не покажет —
   ориентироваться на `longTasks`/`SH`, а не на p95.
4. Для стенда без телефона: `node tools/vk_perf_cdp.mjs --url <URL> --w 844
   --h 390 --dpr 3 --seconds 20 --cpu 4 --out docs/qa-vk-perf` (эмуляция
   телефона + CDP-профиль), либо мои probe'ы ниже.
